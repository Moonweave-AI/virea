# 模型优化现状与探索基线

## 1. 当前结论与使用范围

**当前可以围绕 MotionCraft 建立实验基线，但不能据此认定它已经全面优于 ARDY + SentiAvatar，也不能把已有协作路线的问题统一归因于两个模型互相干扰。** 本文供人工与 AI 配合探索、讨论和记录，不是优化施工方案、生产验收报告或正式模型替换决议。

两条思路可以同时保留：以 ARDY + SentiAvatar 理解已有能力及历史问题；以 MotionCraft 检验“动作描述与语音独立控制”的新方向。先确认产品需要什么输入和输出，再判断问题位于计划、模型、跨模型交接、重定向还是播放层。

| 项目 | 本文采用的基线与边界 |
|---|---|
| 核对日期 | 2026-10-09，北京时间 |
| 代码基线 | `main@4f32acdf6a645431c0d73592c6d7bd7e9530df95`，已包含持续角色和三条动作路线 |
| 探索分支 | `feat/motion-model-optimization/detail-technical-method`；沿用现有 `feat/.../detail-technical-method` 格式 |

| 本次交付范围 | 新建探索分支和本文，追加本地进度日志；不改模型、协议、依赖、运行配置或旧文档 |
| 未纳入范围 | 未合入主线的 VRChat 分支；其他模型选型的全面比较；真实模型部署和性能调优 |

本文使用四种证据口径：**当前事实**来自该基线的代码和配置；**历史记录**来自带日期的报告，不代表本轮重跑；**优化假设**需要实测；**待确认**需要负责人进一步确定目标或提供运行证据。

先前的 `docs/project-understanding-and-maintainer-discussion-2026-10-02.zh-CN.md` 是本次讨论的起点，当时核对的是 `main@78ab06b` 和持续角色分支 `14cce76`。其“角色能力尚未合入主线”的分支状态不能继续套用于本文基线。该旧文件在当前工作区未被 Git 跟踪，本次不顺带提交；本文完整复述所需结论，不依赖读者取得这份本地材料。

## 2. 两次讨论如何衔接

### 2.1 原方向：改善 ARDY + SentiAvatar 协作

最初关注的体验是：角色答应跳舞后，主体动作不充分、反复回到自然姿态，运动期间表情少，结束后又有变化。由此提出检查两个模型的配合关系。

核对后的修正是：这条路线确实围绕 ARDY 与 SentiAvatar，但已有统一计划、时序、身体控制权、运动历史、有限边界约束和执行反馈，并非完全独立生成后简单拼接。历史现象也不只有一个可能原因：计划提前收势、播放等待、模型输出、表情生命周期都需要区分。

因此原方向应保留为“检查已有协作的具体限制”，而不是先认定缺少协作系统，再从零搭建或取消身体控制权约束。

### 2.2 新方向：按输入需求选择 MotionCraft baseline

用户在本次聊天中转述负责人的更新意见：

> 模型部分的技术选型，主要看输入什么；初步体验下来，感觉可以以motioncraft为baseline，输入包括speech 和 text-conditioned motion，同时这两者解耦。

这是一项有初步体验依据的选型建议，不是本文独立完成的质量对比实验，也不是所有产品需求已经验收的结论。

结合当前实现，可以将它收敛为：**暂以 MotionCraft 为实验基线，分别控制动作描述与语音，保持两条时间轨独立，并按需组合随声手势；用实际表现决定是否替换或保留原路线。** MotionCraft 路线已经存在，不需要为了开始讨论再做一套接入。

两次讨论共同追求的是活动、语音、表情和连续性符合用户意图。新的输入契约视角，不会自动解决旧路线暴露的静默表情、语义判断和播放体验问题。

## 3. 已有路线：协作事实与不能成立的归因

### 3.1 职责和控制关系

LLM 编排要说什么、做什么及先后/并行关系；TTS 生成声音。ARDY 根据持续动作描述、身体历史和可用空间约束生成全身姿态及根运动。SentiAvatar 根据音频、文本和表达条件生成随声身体动作及面部数据。

| 场景 | 身体主来源 | 面部和声音 |
|---|---|---|
| 普通聊天，没有可执行的独立身体活动 | 可由 SentiAvatar 驱动，取决于计划分配和输入就绪 | SentiAvatar 面部，TTS 声音 |
| 独立活动期间同时讲话 | 可由 ARDY 驱动 | 仍可播放 SentiAvatar 面部和 TTS 声音 |
| 讲话结束后继续静默舞蹈 | ARDY 可继续 | 没有自然覆盖整个舞蹈的独立语义表情流 |

**同一帧一个身体主来源，不等于同一时刻只能运行一个模型。** 当前调度先兑现满足开始条件的活动分配，并没有“SentiAvatar 永远优先”的规则。面部单独采样；头部、躯干和手臂仍属于身体骨骼，不能把它们与面部形变混为一类。代码支持并行，也不等于每次运行的表情资源都能及时就绪。当前调度与播放的源码依据见第 8 节。

### 3.2 连续性已经做了什么

ARDY 使用身体历史，SentiAvatar 使用其原生 RVQ 尾部和规划历史。未来 SentiAvatar 轨迹已经准备好时，可按实际音频时刻抽取目标，作为 ARDY 的末端约束，再交接身体。

这是一种有条件的跨模型衔接，不是统一潜空间或通用联合采样。未来轨迹尚未就绪时不能使用该约束；当前没有已验证的“ARDY 任意实际姿态无损编码成 SentiAvatar RVQ”的通用闭环。播放层的平滑也不能替代原生模型历史。[既有交接说明](../doc/character/coarse-activity-execution.zh-CN.md)

### 3.3 历史故障与当前缺口分开看

| 讨论中的现象或说法 | 证据与当前判断 |
|---|---|
| 舞蹈被大量站立和收势挤占 | 2026-09-30 报告有直接记录；持续运动条件、完成条件和最终恢复已作分离。不能认定当前所有失败仍是同一原因。 |
| 窗口之间人为停顿 | 2026-10-02 报告记录了回执等待、窗口时钟重置等原因及修复；真实生成迟到和跨模型等待并未因此得到全面消除。 |
| ARDY 控制身体导致 SentiAvatar 全部停止 | 不符合当前面部和身体分开处理的逻辑；需要检查实际资源就绪及表情映射。 |
| 静默动作时语义表情不足 | 当前仍有实现依据：面部轨道依附语音，语音结束后释放表情。程序化待机变化不是持续语义情绪生成。 |
| 取消身体独占即可解决 | 没有证据支持；可能引入同骨骼覆盖，也补不上缺失的表情内容。 |

历史报告见[持续运动意图](../doc/character/persistent-motion-intent.zh-CN.md)和[窗口连续播放](../doc/character/window-continuity.zh-CN.md)。本次没有重跑其中的真实模型或浏览器案例，不把“历史修复成功”扩大为“当前所有请求质量已达标”。

## 4. MotionCraft baseline：“输入”和“解耦”的准确含义

### 4.1 三类内容不要混淆

| 内容 | 在当前角色路线中的用途 | 不是指什么 |
|---|---|---|
| 动作描述文本 | 英文物理动作描述，例如 `A person walks forward.`，用于文本条件动作生成 | 不是台词转写，也不要求用户先提供一段已有动作 |
| 台词文本 | 角色说给用户听的话，交给外部 TTS 合成 | 不等于要求身体执行的动作命令 |
| speech 音频 | 当前通常来自 TTS；动作 worker 接收 PCM，并提取语音特征用于随声手势 | 不表示 MotionCraft 已有语音识别、理解用户口头指令或生成声音的能力 |

### 4.2 已实现的解耦

动作轨有自己的描述、开始时刻和持续时间；语音轨有自己的台词和开始条件，长度以 TTS 实际音频为准。两轨共享播放时钟，但不要求起止对齐。语音可以跨动作边界，动作可以静默继续，也可以没有台词。语音结束不会自动让整个动作停止或归零。

例如，“跳舞 20 秒，第 5 秒开始说一句话”可以表达为一段 20 秒动作与一条独立语音；说完后仍应继续动作。这说明接口能表达该任务，不代表模型每次都能生成自然且符合语义的舞步。

### 4.3 不是一个检查点包办，也不是完全互不影响

MotionCraft 路线使用同一家族的 **T2M（文本动作）和 S2G（语音手势）两套任务检查点**，各自使用对应统计数据。官方分别发布任务检查点；VIREA 增加了独立时间轨、窗口连续推理和结果组合，而不是把这些工程能力都称为上游原生接口。

当前明确身体动作由 T2M 生成。只有 `speech_gestures=true` 的会话段和动作空白处，才按实际语音区间使用 S2G 的上身及手部手势；组合不会替换根运动、腿部和躯干轨迹。明确动作段可以同时播放语音，但默认不让随声手势改写该动作。

所以“解耦”应解释为 **输入内容和时间安排独立，输出按约定范围组合**，不是两个输出在任何情况下都毫无影响，也不是任意动作与任意语音都已经验证可以自然融合。[路线实现说明](../doc/character/unified-motion.zh-CN.md)

### 4.4 选择 baseline 不等于替换完成

当前代码默认仍是 `sentiavatar_ardy`。选择 MotionCraft 会走独立路线，不会静默退回 ARDY 或 SentiAvatar；SynTalker 也是现有可选路线，但本轮不展开选型比较。

MotionCraft 路线目前准备完整表演后再播放，不是低延迟实时流式交互；没有 SentiAvatar 等价的面部表情或音素口型，嘴部预览使用实际语音能量。其原生历史主要在一次完整表演内连续，新回合或打断后没有把实际已执行姿态重新编码为原生模型历史。降低跨家族切换复杂度，也不能直接推导出速度更快、显存更低或动作质量更好。

## 5. 当前可优化点：先定位，再决定改什么

下表是讨论候选，不是已确认缺陷列表、优先级承诺或自动施工排期。

| 可优化点 | 当前依据和适用范围 | 最小验证思路 | 不能直接采用的结论 |
|---|---|---|---|
| 活动意图与持续执行 | 两路线均依赖高层计划；旧路线有过早收势历史，新路线已有短动作描述与独立时长契约 | 分别保存用户请求、实际计划和已执行轨迹，核对目标、顺序、主体时长与收势位置 | 看见站立就认定 ARDY 被 SentiAvatar 抢占；把已修复问题当成新缺陷 |
| 动作与语音独立性 | MotionCraft 已有双轨和受控手势组合 | 固定动作描述、时长、种子和初态，对比无语音、短语音及跨边界语音；检查实际播放与原生输出 | 语音结束就必须结束动作；任意段都应叠加随声手势 |
| 跨模型或任务切换连续性 | 旧路线依赖可用的未来目标；MotionCraft 仍有 T2M/S2G 组合和窗口边界 | 将原生接缝、重定向接缝、播放等待分别记录，检查位置、旋转及速度突变 | 统一模型家族就没有任何接缝；用平滑掩盖语义错误 |
| 静默表情与身体情绪一致性 | 旧路线面部依附语音；MotionCraft 当前没有等价语义面部轨道 | 先确认产品是否要求静默舞蹈持续表情，以及是否必须有音素口型 | 更换身体模型会自动补齐脸部；通道互斥是唯一根因 |
| 跨回合及打断后接续 | 播放层保留状态与原生模型得到真实状态不是一回事，MotionCraft 未实现跨回合原生闭环 | 从非中性姿态打断并发起下一轮，区分实际执行姿态、预测历史和新模型初态 | 单次长表演连续就证明跨回合也连续 |
| 语义质量、延迟与资源成本 | 接口和时序通过不能证明自然度；完整准备、冷启动、规划和推理均可能影响体验 | 同设备、同输入契约下分项测量，并查看完整正常速度录像；先由负责人确定可接受标准 | 单个演示或不同设备的耗时证明某模型全面更优 |

## 6. 建议的最小验证闭环

这里只给出推进讨论所需的最小动作，不启动服务、下载权重或执行新的优化实验。

先固定一个“20 秒明确动作，第 5 秒开始一句短语音”的场景，并确认是否要求静默表情。用 MotionCraft 作为候选 baseline，先用精确计划隔离 LLM 的规划误差，再检查普通对话入口能否生成等价意图。无语音版本可作为同条件对照；是否加入 ARDY + SentiAvatar 对照由人工确定，不把两条路线机械塞进同一个模型接口。

每个样本至少保留：代码提交号、所选路线、模型资产版本、设备与冷热状态、动作文本、实际台词和 PCM 时长、计划与实际时间轴、原生及重定向输出、播放回执、错误和完整正常速度录像。只保留可分享的证据摘要，模型权重、私人声线和角色资产不随本文提交。

先判定四件事：动作主体有没有被语音截短，语音是否按实际长度完整播放，是否有窗口或交接造成的停顿/突变，动作语义是否符合请求。表情与自然度单独评价，不用“零执行错误”代替。若失败，只选择已有证据定位到的那一层开展下一轮修改。

## 7. 尚未确定的决策与验证边界

需要与负责人确认的最小问题是：**MotionCraft baseline 是否首先以独立语音和身体动作成立为目标，暂不要求与 SentiAvatar 等价的表情能力？** 若持续语义表情是首轮硬要求，仅替换身体模型并不满足需求。

其他约束仍未定稿：允许的准备等待时间、跨回合连续性要求、动作语义和自然度的合格标准，以及最终是否切换默认路线。本文不替负责人设置这些阈值，也不新增模型训练、视觉反馈或面部模型的实施任务。
